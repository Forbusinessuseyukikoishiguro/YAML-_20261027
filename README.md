## はじめに

エンジニアの文章で困るのは、技術的な内容よりも「伝わり方」であることが多いです。

- 「適宜対応します」と書いて、何を・いつまでか伝わらない
- 上司に確認を頼んだものの、結論がどこにあるか分からない
- Jiraのチケットに「動かない」とだけ書かれ、担当者が再現に時間を取られる

これらを減らすために、**テクニカルライティングのレビュー、上司向けの文章、Jiraの記載文**を作るClaude Skill `tech-writing-review-jira-skill` を作りました。

:::message
このスキルは、SKILL.md と参照ファイル（reference）で構成した手順書です。出力は必ず人が読み直してから使ってください。
:::

## スキルの3つの機能

| 機能 | 目的 | 主な出力 |
|---|---|---|
| レビュー | 曖昧な表現や論理の飛びを見つける | 指摘と修正案（元の文、問題、修正文、理由） |
| 上司向け文章 | 判断に必要な情報を先に出す | 件名、冒頭3行、詳細 |
| Jira記載 | 担当者が迷わず着手できるチケットを作る | 件名、説明、完了条件 |

## 工夫した点

### 1. 曖昧語を「具体的な条件」に置き換える

レビューでは、次のような言葉を探します。

- 適宜、なるべく、いい感じ、早めに、少し

それぞれを、期限や数値、対象に置き換えます。

| 元の文 | 修正文 |
|---|---|
| 適宜テストをお願いします。 | 次の3項目をテストしてください：ログイン、パスワード再設定、ログアウト。期限は10/28（水）です。 |
| 処理が少し遅いです。 | 検索処理が平均3秒かかっています（目標：1秒以内）。 |

ポイントは、「どう直したか」だけでなく「どの基準で良くなったか」を書くことです。

### 2. 上司には「件名」と「冒頭3行」で判断させる

上司向けの文章は、次の形にしました。

```markdown
【判断依頼】Jira移行の期限を10/31まで延長するか

結論：移行は10/31まで延長すれば完了できます。
必要な判断：延長するかどうか（A案：延長、B案：現行のまま縮小）
期限：10/27（火）までに回答をお願いします。

（詳細）
...
```

件名だけで「何の依頼か」「いつまでか」が分かると、上司は後ろの詳細を読むかどうかを決められます。

「お時間あるときに」「ご確認いただければ幸いです」のような、期限が書かれていない依頼は避けるようにしました。

### 3. Jiraの件名は「対象＋事象」

Jiraの件名は、一覧で見たときに内容が分かることが大切です。

- 悪い例：「ログインできない」
- 良い例：「ログイン画面で、パスワード再設定後に500エラーが出る」

説明は、次の項目に分けます。

```markdown
## 背景
## 現状
## 期待する動作
## 再現手順
## 影響範囲
## 原因（確認済みと推測を分けて書く）
## 完了条件
```

特に、**原因は「確認済み」と「推測（未検証）」を分ける**ようにしています。推測が事実のように書かれていると、担当者がその前提で作業を進めてしまうためです。

### 4. 完了条件は「確認方法」まで書く

完了条件を「直ったら完了」とすると、担当者によって判断がずれます。そこで、次のように確認方法までセットで書きます。

```markdown
## 完了条件
- [ ] 再設定後、新しいパスワードでログインできる
- [ ] 検証環境で、再設定から3回連続で成功する
```

## 注意していること

### Jiraの項目名は環境に合わせる

Jiraは、プロジェクトの設定によって項目やフィールドの名前が異なります。スキルでは項目名を固定せず、「利用中のJiraの設定に合わせて調整する」としています。公式ドキュメントの最新の情報で確認してください。

### AIの出力を「事実」として扱わない

AIは、もっともらしい原因や影響を書くことがあります。そのため、スキルでは次のルールを入れています。

- 事実にない原因や影響は書かない
- 完了していない作業を「完了」と書かない
- 推測は「推測」と明記する

### 秘密情報をチケットに貼らない

ログやエラー画面には、トークン、パスワード、個人情報が含まれることがあります。チケットに貼る前に、必ずマスクします。

```text
Authorization: Bearer <TOKEN>
user_email: <EMAIL>
```

## 使ってみた感想

文章を直す作業は、技術的な内容の確認よりも時間がかかることがあります。特に、上司に送る前の「判断に必要な情報が揃っているか」の確認は、スキルのチェックリストに落とし込むと抜け漏れが減りました。

一方で、どの程度の具体性が必要かは、上司やチームによって異なります。スキルの出力をそのまま使うのではなく、普段のやり取りに合わせて調整するのが現実的です。

## まとめ

技術文書の品質は、正しい内容を書くことに加えて、**読み手が次に何をすればよいか分かること**で決まります。

- 曖昧な表現を、期限・数値・対象に置き換える
- 上司には、件名と冒頭3行で判断させる
- Jiraには、再現手順と完了条件を書く
- 原因は、確認済みと推測を分ける

同じ悩みを持つ方の参考になれば幸いです。
